Course overview

In this course, riggers use Claude as a coding partner to build a working rigging framework of their own, from an empty folder to a tool that builds, saves and rebuilds a rigged asset.

A rigging framework is more than an auto-rig. It covers the whole workflow of building a rigged asset: the code that wraps Maya nodes, naming rules, reusable rig components, data that is exported and imported between builds, and the UIs artists use every day. The course builds each of those layers in order, so every layer rests on the one under it.

The central idea is to copy Maya's own node hierarchy in Python. Students start with a Node class, then derive DG and DAG classes from it, the same way Maya does. Each class can reach its attributes through attribute objects. Once that foundation exists, every later tool is shorter, easier to read and easier for Claude to extend.

Who this course is for

The course is for riggers and technical artists who know Maya but have never built a framework, and may never have written more than a few lines of code.

  • Riggers who rig by hand or with someone else's auto-rig and want their own system.
  • Technical artists with some MEL or Python snippets who want to grow them into a real codebase.
  • Rigging leads who want a pipeline their team can maintain and extend with AI.

No programming background is required. Claude writes most of the first draft of the code; students learn to read it, question it, test it in Maya, and direct the next change. Python basics are taught as they come up, not as a separate lecture.

What you will be able to do

By the end of the course, each student owns a framework that rebuilds their asset from a single build.py script. They can also explain every layer of it.

  1. Set up a Maya + VS Code + Claude Code workspace and send code from VS Code to Maya.
  2. Describe a coding task to Claude clearly, review what it writes, and test it in Maya before accepting it.
  3. Write a naming convention and the functions that parse and build names from it.
  4. Wrap Maya nodes in Python classes (Node, Dg, Dag, Joint, Controller) that mirror Maya's own node types.
  5. Use an Attr class to read, set, lock, hide and connect attributes with short, readable code such as ctrl.attr('ty') >> grp.attr('ty').
  6. Write a rig base class that names, tags and groups every node a component creates.
  7. Build rig components, from a FK chain to a full arm with IK/FK switching, on top of that base.
  8. Export and import the data a rebuild needs: guides, skeleton, control shapes, skin weights, blendshapes and attribute values.
  9. Build simple Qt UIs that artists use to run builds and data tools.
  10. Keep the framework healthy with version control and conventions that Claude follows.

How the course is taught

Every module uses the same loop: understand the rigging idea, ask Claude to build it, test it in Maya, then improve it.

  1. Concept. The instructor explains the rigging problem in Maya terms first, with no code. For example: what a zero group is for, or why DAG nodes have paths and DG nodes do not.
  2. Design. The instructor shows where this layer sits in the framework: its file, its classes and what it may import. Students know what they are building before they ask Claude for it.
  3. Prompt. Students describe the module to Claude in plain language. They give it the naming rules and the classes already written.
  4. Test in Maya. Students run the code, read any errors, and paste them back to Claude. Learning to debug this way is a core skill.
  5. Review and own it. Students ask Claude to explain each line they do not understand, then make one change by hand.

The framework layout

Students build the framework from scratch. It follows a layout designed for production rigging: each layer is one file or folder, and each module adds the next one. By the end, every student's myrig/ package has the structure below.

File in myrig/What it teaches
naming_tools.pyNaming convention [side_]{module_}[desc_]{type}, parse() and build()
core.pyConstants such as Side and Color; Node → Dg / Dag → Joint, Controller; creation helpers
decorator.pyundo_chunk, preserve_selection, timer
attr.pyAttr class: get, set, lock, hide, connect with >>
stubs/Stubs generated from Maya, so the editor autocompletes every node type without a wrapper class per node
components/_base.pyBaseRig, BodyBase: init_node(), add_controller()
components/rig_main_group.py, rig_fk.py, rig_arm.pyReal components, from simple to complex
io/data_io.pyWriting and reading skin, blendshape, curve, skeleton and attribute data
io/rig_builder.pyRunning a build.py from a clean scene
ui/Workspace UI, asset browser, rigging toolbox

Working with Claude

Students keep a CLAUDE.md file at the root of their framework. It records the naming convention, the class hierarchy and the coding style. Claude reads this file every session, so its code stays consistent with the framework as the framework grows. Students update the file at the end of each module.

Syllabus

The course has 12 modules in four parts. Each module ends with a lab whose result is added to the student's own framework.

The modules run bottom to top. The Node classes layer (Modules 4 and 5) is the foundation every layer above it calls.

Part 1 — Foundation

Module 0: Setup and working with AI

Students set up the tools and learn the prompt, test and review loop before writing any rigging code.

  • Install VS Code, Claude Code and the Maya Python extension; connect VS Code to Maya's command port.
  • Create the framework package (myrig/__init__.py) and add it to Maya's Python path.
  • How to ask Claude for code: give context, state the result you want, ask for one small step at a time.
  • Reading a Maya error message and handing it back to Claude.
  • Git basics: commit after each working step.
  • Lab: ask Claude for a script that creates a joint chain from selected locators, then run and fix it.

Module 1: Naming tools

Students write the naming convention that every node in their rigs will follow, plus the code that enforces it. This code is plain Python with no Maya calls, so it is where students learn the Python they need.

  • Python for riggers: variables, lists, dicts, functions, classes, imports, maya.cmds vs maya.api.OpenMaya.
  • Designing a convention: [side_]{module_}[desc_]{type}, for example lft_ik_arm_ctrl or lft_fk_arm_1_jnt.
  • Choosing type suffixes: ctrl, zr, ofst, jnt, grp, crv and utility-node suffixes.
  • parse(name) splits a name into side, descriptions and type; build(side, names, type_) joins them back.
  • Mirroring names left to right; camelCase helpers for attribute names.
  • Lab: write naming_tools.py, then ask Claude to write tests for parse() and build().

Module 2: Core — the framework's skeleton

Students set up the shared building blocks that every later module uses.

  • Constants as small classes: Side (lft, rgt), Color, rotate orders, operators.
  • Decorators that make tools safe for artists: undo_chunk, preserve_selection, timer.
  • How modules depend on each other, and why core must not import from components.
  • Lab: create core.py with Side and Color, and decorator.py with undo_chunk.

Module 3: The attribute class

Students wrap Maya attributes in an Attr class so rig code reads like a sentence.

  • Attr('ctrl.tx'): value, lock, hide, keyable, exists, type, children.
  • Python properties: why attr.lock = True is easier to read than a setAttr call.
  • Operator overloading: src >> dst to connect, attr[0] for multi attributes.
  • Compound attribute classes: XyzAttr, RgbAttr.
  • Lab: build attr.py and rewrite a 20-line cmds script with it.

Module 4: Node classes — Node, DG and DAG

This is the core idea of the course: students rebuild Maya's node hierarchy as Python classes, and every later tool stands on it.

  • How Maya organises nodes: dependency (DG) nodes vs DAG nodes with transforms, shapes and paths.
  • Node: holds the MObject, name, attr(), add() to add attributes, lock and hide helpers, get_side().
  • Dg(Node): utility nodes. Dag(Node): parent, children, shape, world position, axes, snapping.
  • Specialised classes: Joint(Dag), Controller(Dag) with shape library, colour and scale.
  • Why names alone break (renames, duplicate names) and how MObject and MDagPath solve it.
  • Lab: build core.py's class hierarchy; create a controller, colour it, parent it under a zero group.

Module 5: Dynamic attributes and generated stubs

Students make every Maya node usable from their framework without writing a wrapper class per node type. They then get editor autocomplete back by generating stubs from Maya itself.

  • Why per-node wrapper classes don't scale: a framework that hand-writes a class per node type grows to thousands of lines, and it never covers them all.
  • Node.__getattr__: md.input1X returns an Attr for any node type, plugin nodes included, in about 15 lines.
  • Guards: Python methods win over Maya attributes (node.name vs node.attr('name')), internal names are skipped, and a typo raises a clear AttributeError.
  • Teach the explicit node.attr('tx') first, then the shortcut.
  • Introspection: reading a node type's attributes from Maya with om.MNodeClass.
  • A stub generator that writes .pyi classes and typed create() overloads, so VS Code autocompletes rc.create('multiplyDivide').
  • When a hand-written class still earns its place: added behaviour, such as BlendShape target management or an operation enum setter.
  • Creation helpers: create(), group(), joint(), locator(), create_control(), constraint shortcuts.
  • Lab: ask Claude to write the stub generator, generate stubs for the student's own node list, then build a stretchy distance setup with autocomplete.

Part 2 — Rig components

Module 6: Rig base

Students write the base class every component inherits from. It decides how nodes are named, tagged and grouped.

  • BaseRig(module, tag, side): the component's meta node and its groups.
  • init_node(node, side, names, type_): names a node by the convention and stores metadata on it.
  • Body helpers: add_controller() creates the zero group, offset and control stack in one call; add_space_blender().
  • The main group: world, global and local controls; ctrl_grp, jnt_grp, still_grp.
  • Lab: write _base.py and the MainGroup component.

Module 7: Basic components

Students build simple, reusable components and learn the pattern every component follows.

  • Component pattern: inputs (guide joints, parent, side) → nodes → connections → outputs other components plug into.
  • FK chain, point (single control), COG, neck and head.
  • Connecting components: parenting to another component's output.
  • Lab: rig a simple prop or tail with MainGroup + Fk components.

Module 8: Limb components

Students build the components that make a character rig: arms, legs and spines.

  • IK/FK arm with a blend switch, pole vector and stretch.
  • Leg with reverse-foot pivots; torso with spline IK.
  • Space switching between parents.
  • Non-roll and twist joints.
  • Lab: rig both arms of the student's character from one component class, using the side to mirror.

Part 3 — Data and build pipeline

Module 9: Data IO

Students export the data that cannot be generated by code and import it back during every build.

  • A workspace folder layout per asset, and functions that find paths in it.
  • The write and read pair: every exporter has a matching importer.
  • Matching data to nodes by name, and what to do when names change.
  • Lab: write data_io.py with control-shape and skin-weight export and import.

Module 10: The build script

Students turn their rig into a script that rebuilds it from scratch, so any change can be rebuilt in seconds.

  • build.py with a main(): import model, import guides, build components, read data, clean up.
  • rig_builder.run(): new scene, run main(), post-build steps (control and joint sets), save .ma.
  • Iteration: change a guide or a weight, rebuild, compare.
  • Lab: rebuild the character rig with one command.

Part 4 — Tool UIs

Module 11: UIs for artists

Students wrap their framework in simple Qt tools so artists can use it without writing code.

  • PySide basics: windows, layouts, buttons, lists; docking a window in Maya.
  • Asking Claude for a UI from a sketch or a description.
  • Keeping UI code separate from rig code: the UI calls framework functions and holds no rig logic.
  • Example tools: workspace and asset browser, data IO panel (export and import buttons), rigging toolbox.
  • Lab: build a workspace UI that picks an asset, runs its build and exports or imports its data.

Advanced track (follow-up course)

The core course covers the full framework. A follow-up course goes deeper into rig development:

  • Facial rigging components and blendshape (FACS) systems.
  • Matrix-based rigging and parallel evaluation performance.
  • A node-graph build editor in place of build.py.
  • Animator pickers and production tools.
  • Testing, versioning and migrating rigs between framework versions.
  • Running the framework across a team and a studio pipeline.

Final project and format

For the final project, each student rebuilds their own asset with their own framework, from a clean scene, with one command.

The final project must show:

  • A framework package with core, naming_tools, attr, rig base and at least four components.
  • A build.py that rebuilds the asset from model, guides and saved data.
  • Control shapes and skin weights that survive a rebuild.
  • One UI that an artist can use to build the rig and export or import data.
  • A CLAUDE.md that describes the framework's conventions.
  • A 5-minute demo: change a guide, rebuild, and show that the data comes back.
